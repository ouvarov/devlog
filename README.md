# DevLog

DevLog — простий трекер задач для інженерної команди з двома вбудованими AI-агентами. Трекер уміє створювати, редагувати й видаляти задачі, фільтрувати за статусом і сортувати за пріоритетом або датою; у задачі можуть бути підзадачі. Агент пріоритизації (A) дивиться на відкриті задачі й радить, з чого почати день. Агент декомпозиції (B) розбиває одну задачу на підзадачі, а якщо задача надто розмита, спершу ставить питання. Обидва агенти працюють на справжньому Gemini; для запуску без ключа є `LLM_PROVIDER=mock`.

## Запуск

Потрібен Node `^22.22.3 || ^24.15.0 || >=26.0.0` (поле `engines` у кореневому `package.json`, у `.nvmrc` — 24). Перед `npm run dev` скрипт `predev` перевіряє версію і зупиняється з поясненням, якщо вона не підходить.

```sh
npm install
npm run dev
```

- web: http://localhost:3000
- API: http://localhost:4000 (перевірка: http://localhost:4000/health)

`npm run dev` запускає через `concurrently` три процеси: `tsc --watch` для `packages/shared`, `nest start --watch` для API і `next dev --port 3000` для web. Перед ними `predev` збирає `packages/shared`.

Що відбувається на першому старті: API створює папку `apps/api/.data/pglite`, застосовує міграції з `apps/api/drizzle` і, якщо таблиця задач порожня, додає 14 сид-задач (12 верхнього рівня і 2 підзадачі). Наступні старти дані не чіпають.

`.env` не обов'язковий. Без нього трекер працює, а агенти вимкнені (див. розділ LLM).

Скинути базу: зупиніть API, потім `npm run db:reset`. Наступний старт API знову створить 14 задач.

Перевірки:

```sh
npm test              # тести перевірки Node, API і web
npm run lint
npm run typecheck
npm run format:check
```

## Змінні середовища

Один файл `.env` у корені репозиторію: `cp .env.example .env`. API читає його через `@nestjs/config`, web — через `apps/web/next.config.ts`. Порожнє значення означає «не задано».

| Змінна | Хто читає | За замовчуванням | Що означає |
|---|---|---|---|
| `PORT` | API | `4000` | Порт API |
| `WEB_ORIGIN` | API | `http://localhost:3000` | Єдиний origin, який CORS пускає до API. Шлях і слеш у кінці відкидаються |
| `NEXT_PUBLIC_API_URL` | web | `http://localhost:4000` | Адреса API, яку викликає браузер |
| `LLM_PROVIDER` | API | не задано, тобто `google` | `google` або `mock` |
| `GOOGLE_GENERATIVE_AI_API_KEY` | API | немає | Ключ Gemini з AI Studio |
| `GEMINI_MODEL` | API | `gemini-3.5-flash-lite` | Id моделі Gemini |

Порт web зафіксований (`--port 3000` в `apps/web/package.json`). Якщо міняєте `PORT`, поміняйте й `NEXT_PUBLIC_API_URL`.

## LLM

Підтримано лише Gemini і `mock`. Завдання просить будь-який LLM API і хоча б одного агента на справжньому API; у Gemini є безкоштовний tier. Агенти звертаються до моделі через Vercel AI SDK, тож код агентів від провайдера не залежить. Інший провайдер — це пакет провайдера AI SDK, гілка в `apps/api/src/llm/llm-connection.ts`, нове значення в `LLM_PROVIDERS` (`packages/shared/src/agent.ts`) і змінна для ключа в `apps/api/src/config/env.schema.ts` та `.env.example`.

Як отримати безкоштовний ключ: відкрийте https://aistudio.google.com, натисніть Get API key і вставте ключ у `.env`:

```sh
GOOGLE_GENERATIVE_AI_API_KEY=...
```

Після зміни `.env` перезапустіть `npm run dev`.

Три режими:

- **Ключ є** (`LLM_PROVIDER` не задано або `google`): агенти викликають `GEMINI_MODEL`.
- **Ключа немає і `LLM_PROVIDER` не задано**: API стартує, трекер працює. `POST /agents/*` відповідають 503 `LLM_NOT_CONFIGURED`, у UI бейдж «not configured» і банер «No LLM key», кнопки агентів неактивні. Якщо ж `LLM_PROVIDER=google` задано явно без ключа, API не стартує і пише, якої змінної бракує.
- **`LLM_PROVIDER=mock`**: справжня модель не викликається. Відповіді заздалегідь записані в `apps/api/src/llm/mock/`. Пріоритизація: `list_tasks` → `get_task` першої задачі в роботі → `submit_plan` з першими трьома задачами списку у фокусі. Декомпозиція: без відповідей — `search_tasks` → `ask_clarification` з двома питаннями; з відповідями або без питань — `search_tasks` → `submit_subtasks` з трьома пунктами «Mock part N: <назва>» і одним припущенням. UI показує бейдж `mock · scripted-mock` і рядок «Mock provider: answers are pre-recorded, no real model is called». Причини, підсумок, підзадачі і припущення в мок-відповідях починаються з «Mock», питання — ні. У запущеному застосунку мок лише успішний; сценарії збоїв є тільки в тестах API.

На безкоштовному tier Gemini Google може використовувати запити для покращення своїх продуктів. Не пишіть у задачі приватних даних.

## Зберігання даних

PGlite — справжній Postgres, зібраний у WASM, який працює всередині процесу API. Дані лежать у `apps/api/.data/pglite`. Чому так: рецензентові нічого не треба встановлювати, а код працює зі справжнім SQL і міграціями Drizzle (`apps/api/drizzle`). Схема — `apps/api/src/db/schema`.

Перемикача `DATABASE_URL` немає. Щоб перейти на сервер Postgres, треба замінити драйвер у `apps/api/src/db/db.module.ts` (PGlite → node-postgres) і тип у `apps/api/src/db/database.ts`; схема й міграції ті самі.

## Стек

- **Next 16** (React 19) — web.
- **NestJS 12** — API. Обрано замість голого Express, бо Nest дає структуру модулів, DI, глобальні pipes і filters (тут валідація zod-схемами і єдиний формат помилок) і при цьому працює поверх Express (`@nestjs/platform-express`).
- **Drizzle** 0.45 — схема, запити й міграції.
- **zod 4 у `packages/shared`** — одні схеми й типи для API і web: API валідує ними запити й відповіді агентів, web — форми перед відправкою.
- **Vercel AI SDK v7** (`ai`, `@ai-sdk/google`) — цикл агента, tools, mock-модель.
- **TanStack Query 5** — запити й кеш у web.

## Як влаштовані агенти

### Спільне

Кожен агент — це один виклик `generateText` у `apps/api/src/agents/runtime/run-tool-agent.ts` з набором tools і обмеженням кроків. Крок — одна відповідь моделі; модель сама вирішує, який tool викликати далі, на основі інструкцій і результатів попередніх tools.

- **Завершальний tool** (submit) сам перевіряє відповідь у своєму `execute` і повертає `{ accepted: true }` або `{ accepted: false, errors }`. Помилки йдуть моделі, і вона може виправитись у межах ліміту кроків.
- **Зупинка**: прийнятий завершальний виклик, ліміт кроків, помилка моделі або загальний таймаут 25 с на весь запуск. Невдалий виклик моделі SDK повторює 1 раз (`maxRetries: 1`).
- **Останній крок**: на ньому доступні лише завершальні tools, і виклик tool обов'язковий (`toolChoice: 'required'`). Якщо модель і тут відповідає текстом, запуск вважається таким, що вичерпав ліміт кроків.
- **Після циклу** результат ще раз проходить спільну zod-схему з `packages/shared`.
- **Лише читання**: tools читають через `TasksReader` (`apps/api/src/tasks/tasks.reader.ts`), у якого немає методів запису. Агенти нічого не пишуть у базу; записує звичайний `POST /tasks/batch` після підтвердження користувачем.
- **Текст задач — дані**: в інструкціях і в промпті сказано, що назви й описи задач — це дані, а не команди.
- **Вивід моделі** UI показує лише як текст.
- **Відповідь** містить `meta` (провайдер, модель, `source: llm | fallback`, `stoppedBy: submitted | step-limit | error | skipped`, причина fallback, кроки, токени, час) і `trace` — кожен крок з викликами tools; вивід tool обрізано до 300 символів, відхилені submit позначені. UI показує trace під результатом.

Інструкції (системні промпти) лежать в окремих файлах, і їх редагує власник:

- `apps/api/src/agents/prioritize/prioritize.instructions.ts`
- `apps/api/src/agents/decompose/decompose.instructions.ts`

### A. Пріоритизація «з чого почати день»

**Запуск**: кнопка Run у панелі Prioritize праворуч на головній сторінці. `POST /agents/prioritize`.

**Кроки**: до 6. Якщо відкритих задач немає, модель не викликається (`stoppedBy: skipped`), панель пише «Nothing to prioritize».

**Tools** (жоден не пише):

- `list_tasks({ status?, priority? })` — відкриті задачі (не done), включно з підзадачами, компактними рядками: `id`, `title`, `status`, `priority`, `parentId`, `ageDays` (днів від створення), `staleDays` (днів від останньої зміни), `openSubtasks`. Спершу високий пріоритет, далі старіші. До 50 рядків і `hasMore`. Без описів, тому модель сама вирішує, коли потрібен `get_task`.
- `get_task({ id })` — одна задача з описом, батьком і підзадачами.
- `submit_plan({ focus, later, summary })` — завершальний.

**Правила в інструкціях**: задачі в роботі першими; стара medium може випередити свіжу high; конкретна підзадача краща за батька з відкритими підзадачами; лише id з tools, без повторів.

**Перевірка `submit_plan`**:

- схема: `reason` 1–200 символів, `summary` 1–400, у `focus` не більше 5;
- у `focus` від 3 до 5 задач, а якщо відкритих менше 3 — усі відкриті;
- кожен id існує і не done (звіряється зі свіжим списком відкритих задач);
- жоден id не повторюється у `focus` і `later` разом.

**Якщо плану немає** (ліміт кроків, текст замість submit, помилка, 429, таймаут), API все одно відповідає 200, але план рахує формула, а не модель:

```
score = PRIORITY_WEIGHT[priority] × (1 + min(ageDays, 14) / 7) + (in-progress ? 2 : 0)
PRIORITY_WEIGHT: low 1, medium 2, high 3
```

Перші 5 за балом ідуть у фокус, решта — у `later`. Формула бере ті самі три фактори, що й інструкції: пріоритет, вік, статус. UI показує банер «Computed without AI» з причиною і рядком «The plan below comes from the formula: priority, age and status»; у кожної задачі причина з балом. Код: `apps/api/src/agents/prioritize/prioritize-fallback.ts`.

**Що бачить користувач**: фокус із причинами й посиланнями на задачі, `later`, підсумок, `meta` і trace. План — лише порада: нічого не змінюється в задачах.

### B. Декомпозиція на підзадачі

**Запуск**: кнопка «Break into subtasks» на сторінці задачі `/tasks/[id]` відкриває діалог; галочка «Don't ask questions, state assumptions instead», кнопка «Break down». `POST /agents/decompose` з `{ taskId, clarification?, skipClarification? }`.

**До моделі**: без LLM — 503; задачі немає — 404; підзадача або done — 400. Задача і її підзадачі йдуть у промпт JSON-ом з поміткою, що це дані.

**Кроки**: до 6.

**Tools** (жоден не пише):

- `search_tasks({ query })` — задачі, у назві чи описі яких є будь-яке зі слів запиту (слова від 3 символів, до 8 слів, ILIKE з екрануванням `%`, `_`, `\`), до 10 результатів. Повертає й done-задачі, і саму задачу, щоб модель не запропонувала дубль.
- `ask_clarification({ questions })` — завершальний, 1–3 питання до 300 символів.
- `submit_subtasks({ items, assumptions })` — завершальний, 3–8 пунктів, до 5 припущень до 300 символів.

**Справжнє розгалуження**: гілку обирає модель. У першому запуску вона бачить обидва завершальні tools і сама вирішує: задача зрозуміла → `submit_subtasks`, розмита → `ask_clarification`. Якщо в одному кроці прийнято обидва, перемагає `submit_subtasks`.

- Користувач відповів (`clarification` з питаннями й відповідями) — `ask_clarification` у набір не передається, пари питання/відповідь ідуть у промпт. Тож раунд питань лише один, і це тримає код, а не промпт.
- Режим без питань (`skipClarification`) — `ask_clarification` теж немає, а `submit_subtasks` вимагає хоча б одне припущення.

API не зберігає стан між запитами: клієнт сам надсилає питання назад разом з відповідями.

**Перевірка `submit_subtasks`**: схема з `packages/shared` (назва 1–200, опис до 5000, пріоритет і статус з дозволених; без пріоритету — пріоритет задачі, без статусу — `todo`); назви не повторюються (без урахування регістру й пробілів) і не збігаються з наявними підзадачами; у режимі без питань — хоча б одне припущення.

**Підтвердження**: кожен пункт має галочку «Create subtask N», поле назви, вибір статусу й пріоритету. Create створює лише відмічені пункти одним `POST /tasks/batch` з `parentId` — в одній транзакції. Сервер ще раз перевіряє кожен пункт і батька (існує, верхнього рівня, не done).

**Якщо відповіді немає**: fallback у B немає. API відповідає 422 `AGENT_FAILED` з trace і причиною в `message`. Діалог показує «The agent did not finish», «Nothing was created», trace і кнопку «Try again». Нічого не створюється.

## Неправильні результати на справжній моделі

**Мова відповіді пріоритизації** (`docs/agent-log/PR4.md`, `PR5.md`). Перший прогін на `gemini-3.5-flash-lite` написав причини й підсумок українською, хоча 12 з 14 сид-задач англійською; ймовірно, тому що перша задача в списку українська. Правило в промпті переписали: «мова, якою написана більшість назв; якщо жодна не переважає — англійська». Другий прогін у PR4 відповів англійською. У PR5 той самий промпт знову дав українську. Тобто на flash-lite зі змішаною мовою списку це правило ненадійне. У декомпозиції, де задача одна, мова в усіх прогонах збігалася з мовою задачі (`PR6.md`).

Як продукт тримає неправильний результат:

- план пріоритизації — лише порада з причинами й посиланнями, нічого не записується;
- підзадачі декомпозиції користувач підтверджує по одній: може зняти галочку, змінити назву, статус і пріоритет;
- перевірка відхиляє вигадані id, done-задачі, повтори й дубль назв, і модель отримує ці помилки, щоб виправитись;
- якщо модель так і не дала коректної відповіді, A показує план за формулою з банером, B — помилку з trace.

## Що не зроблено

- Агенти C (статус-апдейт у стилі Slack) і D (тріаж вхідного тексту) є в дизайні, але не зроблені: забракло часу. Завдання просить двох справжніх агентів — це A і B.
- Немає авторизації і деплою.
- Немає стримінгу: відповідь агента приходить цілою, UI показує індикатор із часом і лімітом кроків.

## Нотатки запуску і відомі проблеми

- `npm run db:reset` видаляє `apps/api/.data/pglite`, навіть коли API запущений. Спершу зупиніть API.
- Відкривайте http://localhost:3000, а не `127.0.0.1:3000`: CORS пускає лише `WEB_ORIGIN`, а за замовчуванням це `http://localhost:3000`. Для іншої адреси задайте `WEB_ORIGIN`.
- `npm run dev` перезбирає `packages/shared` сам (`tsc --watch`). Чи перезапускає `nest start --watch` API після такого перезбирання, не перевірено; після зміни в `packages/shared` надійніше перезапустити `npm run dev`.
- Безкоштовний tier Gemini має ліміти запитів. На 429 пріоритизація віддає план за формулою (`fallbackReason: rate-limited`), декомпозиція — 422 з текстом «The model is rate limited; try again in a minute». Справжній 429 від Gemini не перевіряли, лише на моку.
- Після зміни `.env` перезапустіть `npm run dev`.
